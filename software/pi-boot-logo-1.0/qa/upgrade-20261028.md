# New Cam 1.0 boot 升级与回退 · 离线验收

日期：2026-10-28。范围仅为 `pi-boot-logo-1.0/boot_system.py`、`VERSION`、新增 `tests/test_upgrade.py` 和本记录。没有构建包、连接 Pi、重启、操作 GPIO、删除文件，旧 `pi-boot-logo-test` 源码和已发布包未改。

## 固定接口与状态

- `VERSION=1.0.0`，主题 `newcam`，发布主题文件 `newcam.plymouth`、`newcam.script`、`logo.png`。命令仍为 `probe|enable|verify|rollback --bundle --expected-manifest-sha256`；`enable` 验证可信 manifest 哈希和五个固定发布文件。
- 1.0 独立 state：`/var/lib/junshu-camera-boot-1.0.0/state.json`；独立备份：同目录 `backups/`；FAT 救援备份：`/boot/firmware/junshu-newcam-1.0-backups/`；主题目录：`/usr/share/plymouth/themes/newcam/`；config 标记：`BEGIN/END JUNSHU NEW CAM 1.0`。旧 0.1.1 state、备份、主题均保留。
- `probe` 在旧 0.1.1 已启用时先核对旧 state 的 0600 权限、四个当前文件的哈希/模式、原件备份及 FAT 救援备份、旧主题、config/cmdline 结构和旧生成 initramfs，再允许 1.0 升级。旧 `initramfs8` 已由 0.1.1 生成，故只核对 `kernel8.img` 与打包内核的映射，并通过旧 state 的原件哈希核对打包 `initrd.img-*`；不会把旧主题 initramfs 与原 initrd 不同误判为故障。
- 新 state 记录旧 state 的 SHA-256。重复 `enable` 校验后返回 `changed=false`；1.0 `rollback` 精确恢复本次安装前的四文件（旧 0.1.1 已启用时即恢复其启用状态），保留旧 state 原字节，旧工具随后仍可 `verify`、`rollback`。无 1.0 state 的 `rollback` 返回 `ok=true,status=no_op,changed=false`。
- 启用/回退同时持有旧版与 1.0 的 `/run/lock` 锁。已知的 0.4.0 XDG 链或 1.0 labwc session 链可通过启动前提检查；后者要求旧 XDG 条目准确隐藏、labwc hook 为已知字节、1.0 session state 为 active，且 `start-session.sh` 与其 app manifest 哈希一致。
- 失败时尝试自动恢复四个原文件并留存失败 state、主题和备份。任何当前文件、旧备份、旧 state 权限或新 state predecessor 异常均拒绝覆盖。

## 测试

命令：

```sh
cd camera-project/C-软件/pi-boot-logo-1.0
PYTHONDONTWRITEBYTECODE=1 python3 -B -m unittest discover -s tests -p test_upgrade.py -v
```

最终结果：**12 tests，全部通过**。覆盖旧 0.1.1 active→1.0→verify→重复 enable→rollback→旧版 verify/rollback；无结尾 LF 的 cmdline 原字节保留；无旧安装的直接启用与回退；旧当前文件/备份/state 权限篡改拒绝；1.0 当前文件/前驱记录篡改拒绝；`mkinitramfs` 失败后自动恢复并可重试；initramfs 原子替换阶段失败后恢复；旧锁占用时拒绝；无 1.0 state 回退 no-op；已知 1.0 session 链通过。测试 fixture 用独立目录保留在 `qa/r4-boot-logo-20261028/test-fixtures/newcam-1.0-*`，没有清理。

## 交接边界

`pi-boot-logo-1.0/MANIFEST.sha256` 仍是复制目录时的旧清单；主题文件与最终清单由 root/打包负责人统一完成后，应重新生成并验证。这里的模拟 initramfs、文件哈希与回退测试证明本地逻辑，不等于 Pi 下一次实际开机的 Plymouth 画面和桌面可见性验收。
